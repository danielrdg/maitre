# Spike: `claude --resume` in a new herdr tab (M3b parking)

Date: 27-11-2026. Linux, Claude Code 2.1.332, herdr 0.8.2, subscription (OAuth) login, `--model haiku`, `gh` 2.63.2.

M3b parks quiet rooms (stops their Claude) and wakes them with `claude --resume <session-id>` in a new herdr tab. This spike answers what that looks like from the outside, and how maître can tell a good resume from a bad one.

## Setup and isolation

- Own herdr session `maitre-m3b-spike`; `MAITRE_HOME`, `XDG_CONFIG_HOME` and `XDG_DATA_HOME` pointed at a temp dir; throwaway folders as room dirs. Nothing of the real install was used.
- The real `HOME` was kept so Claude Code's login works. Consequence: Claude wrote its session transcripts under the real `~/.claude/projects/` (folders named after the temp paths). Those are the only traces outside the temp dir.
- Rooms were started with `claude --settings <file> --permission-mode auto --model haiku '<tiny prompt>'` with maître's own hook script (`hooks/maitre-hook.mjs`) registered, plus a raw `cat` hook to see the untrimmed payloads (maître's trimmed line drops `source`). The prompt was "reply with the word ok".
- **Gotcha that cost a re-run:** a herdr server started from inside another Claude Code session inherits its `CLAUDE_CODE_*`/`CLAUDECODE` markers, and every Claude in its panes then prints "Transcript saving is off" and writes no transcript, so there is nothing to resume. `cleanEnv` in `src/env.ts` exists for this; the spike server had to be started with those variables unset. `ensureServer` already does that.
- Sample sizes are small (1–2 runs per case).

## TL;DR

1. **Resume works and keeps the id.** In a new tab, `claude --resume <id>` fires `SessionStart` with the **same `session_id`** and `source:"resume"`, 0.9 s after the command is typed (n=1). The agent was `idle` in herdr 3–4 s after typing (n=3). Original prompt and reply were replayed on screen.
2. **Unknown id: error, no picker.** Prints `No conversation found with session ID: <id>`, exits 1 within ~1.5 s, returns to the shell. No `SessionStart`; a lone `SessionEnd` with `reason:"other"` and the bogus id arrives. herdr shows `claude` / `unknown` for about a second, then `agent_not_found`.
3. **An id from another folder is NOT an error.** It resumed normally from a different cwd, with the same id and `source:"resume"`. The session continues **in the new tab's cwd**. So a wrong folder does not fail loudly: maître must start the wake in the room's own dir.
4. **A session that is still live can be resumed again** without error (the old Claude kept running in its tab; the new one showed a Remote Control notice, which may be a side effect of that overlap). Wake must make sure the parked Claude is really gone first.
5. **No prompt on resume**, except the folder-trust dialog when the cwd was never trusted: herdr reports `blocked`, no `SessionStart` until it is answered, then it fires with `source:"resume"`. Untested: Claude Code's "resume from summary / full" question for large or old sessions (the sessions here were one turn).
6. **Picker only appears when no valid id is given** (bare `--resume`, or a string that is not an id, which is treated as a search term). herdr reports it as `idle`, so status alone cannot tell it from a good resume. It fires no `SessionStart`.
7. **Detection recipe:** wait for a `SessionStart` (main agent) whose `session_id` equals the expected one, after the command was typed. See the end.

## 1. Same id, SessionStart, source

Timeline of one room (seconds from its first event; `<id>` = the first session id):

| t | event | session |
|---|---|---|
| 0.0 | SessionStart `source:"startup"` | `<id>` |
| 2.0 | UserPromptSubmit | `<id>` |
| 3.9 | Stop | `<id>` |
| 35.4 | SessionEnd (after `/exit`) | `<id>` |
| 46.0 | SessionStart `source:"resume"` (0.94 s after `pane run`) | `<id>` |
| 47.4 | InstructionsLoaded | `<id>` |

Raw `SessionStart` payload on resume (trimmed, paths neutralized):

```json
{"session_id":"<id>","transcript_path":"~/.claude/projects/-tmp-room/<id>.jsonl","cwd":"/tmp/room","hook_event_name":"SessionStart","source":"resume","seconds_since_last_response":42,"context_tokens":53263,"prompt_cache_likely_expired":false,"estimated_cache_write_usd":0.0107}
```

- `source` values seen: `startup`, `resume`. maître's hook line (`hooks/maitre-hook.mjs`) does **not** keep `source`, so today the events file cannot tell them apart; the session id match is enough (a fresh session always has a new id).
- `SessionEnd` on `/exit` is logged by the hook (`reason:"prompt_input_exit"` per the [earlier spike](2026-11-25-hooks-and-herdr.md); not re-measured here). When Claude is killed instead of exited, `SessionEnd` may not arrive; this was not tested.
- In the logged events, resuming produced no new `UserPromptSubmit` (the hook line showed none after the `SessionStart`); the old conversation was shown on screen.

## 2. Unknown id and an id from another folder

Unknown id (`00000000-0000-4000-8000-000000000000`):

```
$ claude --resume 00000000-0000-4000-8000-000000000000 …
No conversation found with session ID: 00000000-0000-4000-8000-000000000000
EXIT=1
```

- herdr: `agent get` returned `{"agent":"claude","agent_status":"unknown"}` at t+1 s, then `agent_not_found` from t+2 s on. The pane is a bare shell again.
- Hooks: no `SessionStart`. One `SessionEnd` with the bogus id and `reason:"other"`, attributed to the room through `MAITRE_ROOM`. **The reducer must ignore a `SessionEnd` whose id is not the room's expected one.**

Id created in another folder, resumed from a tab whose cwd is a different (already trusted) folder:

- Resumed normally: replayed the conversation, same `session_id`, `SessionStart source:"resume"` 0.0 s after the command, `idle` 3 s later.
- `cwd` in the hook payloads is the **new** folder. `SessionStart.transcript_path` pointed at the new folder's project dir, while the next `InstructionsLoaded` still pointed at the old one, which is inconsistent. Why (a copy, a link or just a stale path) was not investigated; do not rely on the transcript path staying stable.
- The original Claude (still running in its own tab) was not disturbed, and no error appeared in either tab.

## 3. Prompts on resume and herdr's classification

| Situation | herdr `agent_status` | `SessionStart` | Notes |
|---|---|---|---|
| good id, trusted cwd | `unknown` ~3 s, then `idle` | yes, `source:"resume"` | no prompt |
| good id, cwd never trusted | `blocked` from ~2 s | not until answered | folder-trust dialog ("No, exit" is preselected); `down enter` accepts; then `SessionStart` fires and status goes `idle` |
| unknown id | `unknown` ~1 s, then `agent_not_found` | no | exit 1, shell prompt |
| bare `--resume` or non-id string | `idle` | no | picker "Resume session"; a non-id shows "No sessions match …"; only `InstructionsLoaded` events with throwaway session ids appear |
| good id, session already live elsewhere | `idle` | yes | works; both Claudes run |

Not exercised: the long-session "resume from summary" question, an expired login, a session file deleted by cleanup.

## 4. Recipe for Task 4: telling a good resume from a bad one

Success signal: a `SessionStart` line in the room's `events.jsonl`, written **after** the wake command was typed (record the file offset first, as `openRoom` does with `sessionStarted`), with `session === <expected id>` and from the main agent. The main-agent check is an **assumption**: no subagent was run here, so `agent_id` being absent on the main `SessionStart` was not observed (`openRoom` already relies on it). Observed 0.9 s after typing in one run (n=1); herdr only says `idle` at 3–4 s (n=3), so do not wait for herdr.

Poll the events file every 200 ms and herdr (`agent get`) every 1 s. Overall deadline **15 s**: about 15× the one observed delay and 4× the time herdr needed for `idle`, a margin for a cold start or slow disk. It is a judgment, not a measured percentile.

**Precedence:** a main `SessionStart` with the expected id wins over anything else seen in the same poll (blocked, `agent_not_found`, picker text, a stray `SessionEnd`): the resume worked. Otherwise, evaluate in this order:

1. **Trust dialog.** `agent get` says `blocked` and `pane read` shows the dialog's own option lines (the `YES`/`NO` patterns in `src/trust.ts`): wait up to the existing trust timeout (**30 s**, `handleTrust`) for a `SessionStart`. If it is still blocked then, the room stays blocked and the wake reports "answer the folder-trust question in its tab". A `blocked` **without** the dialog text is something else (a question, a permission): needs the user too, report it as such, never assume trust.
2. **Failed resume.** `agent_not_found` (or `pane get` showing a bare shell) counts as failure only after Claude was seen (`unknown`, `idle` or `working`), or after **5 s** from typing the command with no `SessionStart`. Before that, a shell that has not launched Claude yet looks the same. Then `pane read` and look for `No conversation found with session ID` to record the reason. Detected at about 2 s in the unknown-id run.
3. **Picker.** At every poll where `agent get` is `idle` and there is no `SessionStart`, `pane read` the tab: the picker shows `Resume session` and a search box (`Search…` or the typed text, `No sessions match …`). On that text, fail at once instead of waiting for the deadline; close the tab and send no keys.
4. **Deadline** with an agent still `idle`/`unknown`, no `SessionStart`, no dialog or picker text: hung start. Treat as failed, read the pane for the reason, close the tab.
5. A `SessionStart` or `SessionEnd` carrying another id never decides the verdict.
6. Wrong folder is invisible to all of the above. Start the tab with `--cwd <room dir>`, and optionally check the `cwd` of the `SessionStart` payload (maître's trimmed line does not keep it today).

Before waking: confirm the parked Claude is gone (`SessionEnd` seen, or `agent get` → `agent_not_found`), because a still-live session resumes without complaint and would end up running twice.

## 5. Fixture: `gh pr view --json …` shape


Trimmed copy: 2 of the 30 checks kept; comment and review bodies, the repository, the PR number, the branch, check names, human logins, comment ids/urls and run/job ids replaced by placeholders. Shape notes for the fake gh:

- `statusCheckRollup` items are `CheckRun` (`status` + `conclusion`, `workflowName`, `name`, `detailsUrl`). Only `COMPLETED` with `SUCCESS` or `SKIPPED` was captured. - `latestReviews` is the latest review per author; `state` was `COMMENTED` or `APPROVED` here. `id` and `commit.oid` were empty strings in the real output of this `gh` version (not a trimming effect), so do not key on them.
- `comments` are issue-level comments only, not inline review comments. Each has `id`, `author`, `authorAssociation`, `body`, `createdAt`, `url`, `isMinimized`, `reactionGroups`, `viewerDidAuthor`.
- `reviewDecision` was `APPROVED`; it is an empty string when no review is required or none was given (GraphQL schema, not captured).
- An open PR would have `state:"OPEN"`; this one was `MERGED`.

## Cleanup

Server `maitre-m3b-spike` stopped and the temp dirs removed. **Leftover:** Claude Code's own session transcripts for the spike sessions remain under `~/.claude/projects/` (folders named after the temp paths); they were left alone because that directory is the real install's.

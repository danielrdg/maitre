# maître: design

Date: 2026-11-25

This is the English version of the original design spec. Section numbers match the original. Where the spec says "the user", it means the one person who runs maître on their machine.

## 1. Intent and why

maître is an orchestrator for Claude Code agents that runs in the terminal and comes with a pixel-art lounge for watching what the agents do.

The starting point is firstmate, which the author uses day to day. maître makes a few different bets:

- **One room per topic.** firstmate is built around a single liaison: you talk only to the first mate ([README](https://github.com/kunchenguid/firstmate/blob/64254de47a2989add6412949e98c36e3964b24aa/README.md?plain=1#L44)). maître gives each topic its own room, so unrelated requests never share a context.
- **Cleanup on idle time.** firstmate tears a task down after it ships or reports, refusing dirty worktrees and unlanded work ([architecture](https://github.com/kunchenguid/firstmate/blob/64254de47a2989add6412949e98c36e3964b24aa/docs/architecture.md?plain=1#L469)). maître keeps that never-lose-work rule and also closes rooms that sit idle with nothing pending.
- **A small, typed core.** At firstmate commit `64254de4`, the shell scripts under [`bin/`](https://github.com/kunchenguid/firstmate/tree/64254de47a2989add6412949e98c36e3964b24aa/bin) total about 145 thousand lines, and `AGENTS.md`, imported by `CLAUDE.md` ([CLAUDE.md](https://github.com/kunchenguid/firstmate/blob/64254de47a2989add6412949e98c36e3964b24aa/CLAUDE.md?plain=1#L2)), is about 7,350 words. maître aims for a TypeScript core with unit tests and a reception contract capped at 1,500 words.
- **Routing that learns.** firstmate documents dispatch profiles and an optional typed resolver ([architecture](https://github.com/kunchenguid/firstmate/blob/64254de47a2989add6412949e98c36e3964b24aa/docs/architecture.md?plain=1#L367-L371)). maître records each room's outcome and feeds it back to the router.

maître has to be simple to open (one command), keep each conversation in its own place with an automatic name, save tokens by routing the right model per task, clean up what is no longer needed without asking, and show all of it in a lounge that is pretty, light and alive, something you can leave open all day.

The repo is a product for other people too. Whoever clones it must get a complete orchestrator with automatic routing after a guided setup, with nothing of the author baked in. The README has to be as polished as firstmate's.

## 2. Goals, non-goals and anti-goals

**Goals**
- `maitre` in a terminal opens everything: herdr in the `maitre` session, the reception and the lounge.
- Every request goes through the reception, which sends it to an existing room or creates a new one, named after the topic.
- The reception finds the project by itself from an index of repositories. It only asks when it is ambiguous.
- Model routing per task, with outcomes recorded so routing improves with use.
- Automatic cleanup: a room idle for 4 h with nothing pending closes on its own and leaves minutes.
- A real-time lounge that shows states, alerts when someone needs the user, and lets the user answer right there.
- Anyone clones, runs `./setup` (or `maitre setup`), says where their repos live and starts using it. Everything personal (state, memory, local config) stays out of git.

**Non-goals (v1)**
- Other harnesses (Codex, Pi, OpenCode). v1 is Claude Code only.
- Other session managers (tmux, zellij). v1 is herdr only.
- macOS and Windows. v1 is Linux; macOS comes later, without blocking the design.
- Remote or multi-user use. One person, one machine.
- Replacing each repo's CI, review or merge policy.

**Anti-goals (if this happens, it failed even if it works)**
- The lounge hiding a stuck agent. "Needs you" has to be the loudest thing on screen, and the sound has to play.
- Cleanup deleting work that has not left the machine (unpushed commit, uncommitted change).
- The reception piling up context until it gets slow and expensive.
- Becoming another bash orchestrator: critical logic without tests, or instructions that grow without a ceiling.

## 3. Constraints

- Linux, Node 20, herdr 0.8.x, Claude Code 2.1.x, `gh` authenticated.
- The lounge runs in a local browser, with no mandatory build step and no CDN in production. Fonts ship inside the repo.
- No third-party assets: sprites, scenery and sounds are generated by code, as in the v5 mockup. The Pixelify Sans and Silkscreen fonts are OFL and can be redistributed.
- The lounge server listens on 127.0.0.1 only, behind a random token. The token never appears in a process's command line: windows open with a one-time ticket in their command line, which the page trades for the token as a cookie (M2b).
- **Threat model: a single-user desktop.** maître assumes no untrusted local users. On a shared machine another user can race a window's ticket out of the process list while Chrome starts, or take the lounge's old port after a restart moved it and receive an open window's cookie; either way they hold the token, which is permanent until the owner rotates it (stop the lounge, delete `$MAITRE_HOME/lounge.json`). Hardening (rotating the token when the port changes, a 0600 launcher file instead of the ticket in argv) is a follow-up.
- The repo is personal and **public**, named `maitre` (all lowercase, at `danielrdg/maitre`), MIT licensed (the designer's default, same as firstmate).
- **Repo language: English.** README, code, comments, CLI messages and docs are in English. The lounge shows English text by default, with `pt-BR` available as an interface language. This design becomes `docs/design.md` in English.
- **An aesthetic, complete README, in English**, carrying the identity of the neon pixel "maître" logo from the mockup: the Pixelify Sans font, neon pink and gold over lacquer red.
  - The top has a pixel-art banner with the neon sign and a GIF of the lounge.
  - The README also has:
    - badges;
    - "What is it";
    - features illustrated with the sprites;
    - quick start;
    - "How it works" with a diagram;
    - the state map as a table with the characters;
    - configuration;
    - comparison with firstmate;
    - FAQ;
    - credits and license. It must not contain anything from the author's employer or personal setup: project names, state, configs, or real PR names in the mockups.

## 4. Approaches considered

| | How it works | Wins | Loses |
|---|---|---|---|
| **A. Distro + herdr + hooks** (chosen) | A folder with instructions and scripts, plus a CLI and a daemon in TypeScript. Rooms are interactive `claude` sessions in herdr tabs. Claude Code hooks emit events, and the daemon pushes them to the lounge over SSE. | Real interactive rooms (the user walks in and talks), the terminal, skills and plugins the user already has, and a real-time lounge. | Tied to herdr in v1. |
| B. Own app on the Agent SDK | A daemon launches the agents through the SDK. | Full control of cost, queue and state. | Rooms stop being Claude Code; "walking into a room" would need a custom chat. |
| C. All bash | Scripts only, like firstmate's `bin/`. | No runtime dependency. | The author wants the router, janitor and state machine in typed TypeScript with unit tests. |

A was chosen.

## 5. What was decided

- **Name:** maître, with the command `maitre`.
- **Reception + rooms.** Each topic becomes a room with an automatic name. The user can walk into a room and talk to it directly.
- **Project discovered automatically**, like Claude Desktop's "my computer". The user does not `cd` into a project.
- **Cleanup (option A):** a room disappears after 4 h idle, only if nothing is pending. With something pending, it goes to the couch (visibly archived) until resolved. The 4 h are configurable.
- **Models:**
  - Haiku for simple tasks (read, summarize, classify, name, write minutes).
  - Sonnet for the reception, exploration and already-clear changes.
  - Opus for development.
  - Fable as the advisor, consulted before a big decision, when the room is stuck, and before calling something done.
- **Second brain:** a markdown folder with `[[links]]`, Obsidian-compatible, without depending on it.
- **Lounge:** side-view pixel art, based on the v5 mockup, approved as the visual direction.
  - 16x32 characters generated by code, with Pixelify Sans in panels and Silkscreen in names.
  - Party vibe: yellow light, Chinese hall, lots of smoke, casino, a bar with coffee and whisky.
- **Doorman:** at most **6 active rooms** at a time by default (configurable). Rooms on the couch or waiting for merge do not count.
- **Permissions:** rooms run in `--permission-mode auto`. The classifier allows what is safe and only stops on what is risky, and those stops become "needs you" in the lounge. No extra rule for push and `gh pr create`; they follow auto mode's judgment.
- **Several projects = a building.** The facade at night is the overview, and each project is a floor. The ground floor is the lobby (maître's reception, queue on the sidewalk, doorman). The terrace on top is the shared smoking area.
- **State map:**

| State | Where | What it does |
|---|---|---|
| Queued (full house) | Sidewalk | Waits for the doorman (active room cap). |
| New room, planning | Floor bar | Drinks coffee. |
| Working | Floor table | Plays cards; each tool used becomes a card. |
| Subagent reading | Slots | Pulls the lever on each read. |
| Waiting on something outside (CI, build, tests, bot) | Terrace | Smokes; the ashtray fills over time. |
| Consulting Fable | Moon gate / VIP | Talks to the boss with the cigar. |
| Needs you | Lobby reception | Rings the bell, with a red "!" and sound. |
| Ready for you to look (finished the turn without asking anything) | Bar counter | Sits with a colorful drink and a green ✓ balloon. **No sound.** Clicking shows the room's last message. |
| Delivered (PR open) | Bar | Whisky. |
| Merged | Dance floor | Dances, fireworks in the window, then leaves through the door. |
| Parked with something pending | Couch | Naps. |
| Closed | Door | Leaves. |

- **Ambient smoking:** outside the terrace, agents smoke at random: in the queue, playing cards (cigarette in the corner of the mouth), at the bar, on the couch. This is only atmosphere and does not change the state, because **the place tells the state**. On the terrace everyone smokes, always. Each agent draws a "habit" (heavy, light or none), and smoking sessions show up at random moments. All that smoke rises and thickens the haze under the ceiling.
- **Lounge interactions:**
  - Clicking an agent shows its context: task, repo and branch, last steps, time and tokens.
  - If the agent is stuck, it shows the reason, the options (with the recommended one marked) and a free-text field. The chosen answer goes to the room.
  - The slot lever is playable, with a visual and audible jackpot.
  - There is a sound when someone gets stuck, and the sound can be turned off.
  - **A musician with a soundtrack of their own.** Clicking the musician turns the music on or off and picks the style: **calm jazz** or **house/electronic**. The music is generated live by code (WebAudio), with no third-party track, so no copyright.
    - **Jazz:** walking bass, swung ride, ii-V-I chords with soft voicings, and a synthesized sax improvising on the scale.
    - **House:** four-on-the-floor kick, off-beat hi-hat, chord stabs and bass.
    - Volume is separate from the effects, and the musician and the little notes follow the tempo.

## 6. How it works

### 6.1 Pieces

```
~/maitre/                      ← repo clone (the "house")
  AGENTS.md                    ← reception contract (short, with a word ceiling)
  room-AGENTS.md               ← contract appended to each room
  bin/maitre                   ← CLI
  src/                         ← TypeScript: cli, daemon, router, janitor, herdr, hooks
  lounge/                      ← lounge page (canvas + plain JS, local fonts)
  hooks/maitre-hook.mjs        ← one hook for every Claude Code event
  config/                      ← routing.json, capacity, projects.roots (versioned with defaults)
  state/                       ← (gitignored) rooms/, events.jsonl, projects.json, queue.json
  memory/                      ← (gitignored) vault: minutes/, decisions/, preferences.md
```

- **`maitre` CLI:**
  - `maitre` opens or attaches to the `maitre` herdr session, starts the daemon if it is not running, and opens the lounge.
  - Subcommands for the reception and for scripts: `route`, `room open|send|close|list`, `status`, `index`, `janitor`, `stats`.
  - Doors (M2b): `serve` (the daemon, run by the login service), `open` and `prompt` (the lounge and quick-prompt windows), `setup`.
- **Daemon (`maitre serve`):**
  - a single Node process;
  - receives events from the hooks;
  - keeps the room registry;
  - runs the doorman (queue and capacity) and the janitor;
  - serves the lounge (HTTP + SSE) on 127.0.0.1.
- **Reception:** a `claude --model sonnet` session in herdr's "reception" workspace, with the house `AGENTS.md`. It does not work: for each request it calls `maitre route` and acts on the result.
- **Room:** a herdr workspace named `<project> / <room>`.
  - Runs `claude --model <model>` inside the room's worktree.
  - Receives an initial brief and `room-AGENTS.md` (via `--append-system-prompt` or equivalent).
  - Defines Haiku subagents for reading (via `--agents` or equivalent).
- **Single hook:** registered in the Claude Code settings of each room and of the reception.
  - Reads the event.
  - Identifies the room by the `MAITRE_ROOM` environment variable, which maître sets when opening the room.
  - Sends it to the daemon. If the daemon is down, appends it to `state/events.jsonl` for replay.
  - Must be fast and never block the agent.

### 6.2 Life of a request

1. The user writes in the reception.
2. The reception runs `maitre route "<request>"`. The router is a short Haiku call (`claude -p --model haiku`, JSON output, with flags that cut inherited context; see spike 0) with four inputs: the project index, the open rooms (name and one-line summary), recent minutes from the vault, and the routing outcome summary. It returns `{project, room: existing|new, name, task_type, has_code, confidence, question?}`. Haiku **does not pick the model**: code maps `task_type` to a model with the table in section 6.3.
3. When `question` is set (ambiguous), the reception asks the user and routes again.
4. If the room exists: `maitre room send <room> "<request>"` delivers the text via `herdr agent prompt`.
5. If the room is new: `maitre room open`.
   - If capacity is full, the room enters the queue and the reception says so.
   - If there is a seat, maître creates the worktree (`git fetch`, branch `maitre/<room>` from the project's base), creates the herdr workspace, and starts `claude` with the brief.
6. The reception answers the user in one line: where the request went.

The reception's context grows only with these short exchanges. It can be restarted without losing anything, because all state lives in the daemon and on disk.

**The reception does not work, and code guarantees it, not just instructions.** It starts with restricted tools (`--tools`/`--allowedTools`) and a maître `PreToolUse` hook. That hook denies any Bash that is not `maitre …` and any file write. It also starts without the user's personal plugins and hooks that would pull it off its role (for example, a hook that forces brainstorming), via maître's `--setting-sources`/`--settings` (spike 0).

### 6.3 Model routing

- **Base table** in `config/routing.json`: task type to model, applied by code.
- **Inside the room:** reading and gathering go to a Haiku subagent. Fable is the advisor: it uses the account's advisor tool if available, otherwise a subagent with `model: fable`.
- **Learning:** each room records, when it closes, the initial model, model switches, tokens, duration, whether it had to redo work, and the outcome (merged, abandoned). `maitre stats` summarizes this. The summary goes into the router's prompt.
- **Guarantee:** the router never downgrades the model of a room in progress unless the user asks.

### 6.4 States for the lounge

The daemon computes each room's state by combining three sources, in order of trust:

1. **The room's own declaration:** `maitre status working|waiting|blocked "<text>" [--options '<json>']`. `room-AGENTS.md` tells the room to declare waits and blocks.
2. **Claude Code hook events:**
   - tool activity → working;
   - pending permission or a question to the user → needs you, with the options when the event carries them;
   - subagent event → slot;
   - advisor call → VIP (there is no hook for it: it comes from the transcript or a declaration, M5);
   - `gh pr create` → whisky.

   **Bell rule:** it only rings for a real block: pending permission, a question with options, or `maitre status blocked`. A `Stop` with no declaration becomes "ready for you to look", silently, even if the last message is a loose question.
3. **Daemon polling:** `gh pr view` for rooms with a PR (detects the merge → dance floor), idle time (→ couch or exit) and the queue (→ sidewalk).

**Measured mapping** (spike 1, Claude Code 2.1.332; details and payloads in [the spike notes](spikes/2026-11-25-hooks-and-herdr.md)). `main` = an event without `agent_id`.

| Hook | Filter | Lounge state |
|---|---|---|
| `SessionStart` | a new `session_id` resets the room | arrives, idle |
| `UserPromptSubmit` (main) | a `<task-notification>` or `<agent-message …>` prompt is a synthetic resume after a subagent | working; clears a pending block |
| `PreToolUse` | with `agent_id` = subagent activity | working (`tool_name` drives the animation); does not clear a block |
| `PermissionRequest` | `tool_name == "AskUserQuestion"` | needs you: question, options from `tool_input.questions` |
| `PermissionRequest` | any other tool | needs you: permission (`tool_input.command` / `file_path`) |
| `PostToolUse` / `PostToolUseFailure` / `PermissionDenied` | same `tool_use_id` as the block | back to working |
| `SubagentStart` / `SubagentStop` | ignore `agent_type == ""` (a phantom after every `Stop`) | guest added to / removed from the slots |
| `Stop` (main) | `background_tasks` has a `running` task | still working |
| `Stop` (main) | otherwise | ready, silently; clears a block |
| `Notification` | — | no change (the permission one is ~6 s late and generic; the idle one is unreliable) |
| `SessionEnd` | — | leaves |

**Correlating a block.** `PermissionRequest` has no `tool_use_id`, so the reducer pairs it with the most recent pending `PreToolUse` (main or subagent) that has the same `tool_name` and a deep-equal `tool_input`. The block's id is that `PreToolUse`'s `tool_use_id`, and the later `PostToolUse`/`PostToolUseFailure`/`PermissionDenied` with that id clears it. Hook events can be lost (see the spike notes), so a `PostToolUse` or `PermissionDenied` whose `PreToolUse` never arrived must be tolerated: no crash, and the room goes back to working.

- **Permission modes:** in auto mode, actions the classifier allows fire no `PermissionRequest`, and a classifier refusal fires `PermissionDenied` (read from the binary; no refusal was observed).
- **Paths that fire no hook:**
  - a denied permission;
  - Esc;
  - the folder-trust dialog;
  - the auto-mode onboarding overlay.

  The next main `UserPromptSubmit`/`Stop` or herdr's `agent_status` closes those.

### 6.5 Answering from the lounge

The stuck agent's panel sends `POST /rooms/:id/answer` to the daemon. The daemon delivers the answer to the room's tab through herdr: free text via `herdr agent prompt`, and option choice in selection prompts via `herdr agent send-keys`. If delivery cannot be confirmed (`herdr agent read` / `wait`), the lounge shows "couldn't deliver, answer in the tab" with a button that focuses the tab. This is **spike 2**.

### 6.6 Janitor

- Runs every 5 min.
- A room may close when it is past the idle time (default 4 h) and has nothing pending:
  - no uncommitted changes;
  - no unpushed commits (a branch with no upstream counts as unpushed);
  - no open PR;
  - no open question for the user.
- When closing:
  1. Asks Haiku for the room's minutes from the transcript (what was asked, what was done, links, loose ends).
  2. Writes the minutes to `memory/minutes/<date>-<room>.md`.
  3. Closes the herdr workspace.
  4. Removes the worktree with `git worktree remove`, without `--force`, and keeps the branch.
  5. Marks the room as closed.
- With something pending, the room does not close: it goes to the couch and shows the reason in the panel.
- **Merge exception:** when the room's PR is merged and nothing else is pending, the room does not wait 4 h. It dances on the floor for a few minutes and closes with minutes.
- Every decision to close or not close goes to the log, with the reason.

### 6.7 Projects and worktrees

- `maitre index` scans the roots in `config/projects.roots`, which the user sets on first run. It writes `state/projects.json` with, for each repo: name, path, remote and base branch.
- The base branch defaults to the remote's `HEAD` and can be overridden per project, for example `dev`.
- Worktrees live in `~/.maitre/worktrees/<project>/<room>`, created from the local clone, without cloning again.
- The branch prefix is configurable per project (default `maitre/`), to respect each repo's convention.
- Rooms without code get no worktree and run in a scratch folder of their own.

### 6.8 Lounge

- A single page, plain JS with canvas, derived from the v5 mockup. It receives the initial state and then deltas over SSE.
- **Three views:**
  - **building facade**, the default view: one floor per project with an active or pinned room, windows with silhouettes, a floor with someone stuck blinking red, and an elevator to navigate;
  - **floor**: that project's table, slots, bar, VIP, couch and dance floor;
  - **lobby + terrace**: reception, queue and doorman; smokers from every floor.
- The "needs you" alert shows and plays in every view.
- Opens as an app window: Google Chrome `--app=` with maître's own profile (`$MAITRE_HOME/chrome`) and `--class=maitre`. Chromium is not used, because the Ubuntu snap cannot open a profile in a hidden folder ([spike](spikes/2026-11-26-m2b-windows.md)). Without Google Chrome, the default browser opens a tab.
- Pauses drawing while the window is hidden and resumes when it comes back. Sound keeps working via events, not frames.

**Clean interface.**
- The lounge fills the whole window, with no title or legend at the top.
- A corner holds only two pixel buttons: **sound** (on/off) and **names** (always / on hover).
- The model color legend sits behind a small "?" button that opens an overlay.
- The simulation buttons (block, merge, new room) exist **only in `--demo` mode**, grouped in a "demo" menu, because without real agents the scene would stand still. In real use they do not appear.

**Icon and identity.**
- **The icon is the maître himself**, who becomes the project's mascot: a 16x16 pixel-art face with slicked grey hair, a moustache, a red bow tie and a tuxedo.
  - File: a crisp-pixel SVG at `lounge/favicon.svg`, with 192/512 PNGs for the app window and the M2b `.desktop` file.
  - The same mascot appears in the README, in notifications and in the Super+M prompt.
  - The reference drawing is option C of the identity mockup.
- **Tagline: "Your agents' lounge."**
- **Logotype:** "maître" in pixel neon, Pixelify Sans 700, pink glow `#ff5fa2` and text `#ffe0ef`.
- **Palette:** lacquer `#3a130f`, gold `#d9a441`, neon `#ff5fa2`, light `#ffd45c`, ink `#140b08`, plus the model colors.
- **Fonts:** Pixelify Sans for panels, logo and prompt; Silkscreen for names and labels.

**Themes per floor.** Each floor has its own party theme, so the project is recognizable at a glance on the facade and inside the floor.
- The theme changes the skin, not the floor plan. The plan is always the same: table, slots, bar, VIP, couch and dance floor.
- What changes: wall pattern, palette, lighting, the musician's default music, and a signature piece of furniture.
- Initial themes:
  - **Chinese hall:** red lanterns, golden lattice; the v5 mockup.
  - **Neon casino:** purple carpet, signs, more slots; house.
  - **Art deco speakeasy:** dark wood, gold, piano; jazz.
  - **Tiki bar:** bamboo, torches, drinks with umbrellas.
  - **Tokyo karaoke:** blue and pink neon, a small stage with a microphone.
  - **Rooftop garden:** plants, string lights, open sky.
- The theme is assigned automatically the first time the project shows up: the next free one, or a hash of the name when they run out. It can be changed in `config/projects` (`theme: <id>`).
- The lobby and the shared terrace keep maître's own theme: Chinese hall, pink neon.
- With only one active project, the lounge opens straight on its floor. The facade shows up from two projects on.
- In M4, the themes go into the building mockup for approval before code.

### 6.8.1 Using it without a terminal (the four doors)

The terminal keeps working, but the user can use all of maître without opening one.

1. **Clickable reception in the lounge (M2b, done).**
   - Clicking the maître at the lobby desk opens a pixel text box; Enter sends, Esc closes.
   - The request goes via `POST /api/reception` to the daemon. **It goes straight to the router, not to the Claude reception** (owner's decision, 26-11-2026). The daemon saves the text as a request file with the same numbering as the reception hook, then runs the same code as `maitre route` and `maitre dispatch`. That takes about one Haiku call and works whether or not herdr is attached. The cost is free conversation: the box only routes requests, and listing or closing rooms stays in the terminal reception.
   - A router question comes back in a maître speech balloon and the box stays open. The answer is routed together with every earlier text of that conversation.
   - The dispatch lines show in the balloon. When the new room waits on the folder-trust question, or dispatch warned, the box stays open (`needsYou`).
   - One request runs at a time; up to three wait, and more get 429 "the maître is busy, try again". A reply takes at most 150 s.
   - The new room's character walks in through the door.
   - **"Open in terminal", pulled forward from item 2.** A room's panel has a button that focuses the room's herdr tab and opens a terminal on the session (`x-terminal-emulator -e herdr --session <session>`, else `gnome-terminal`). Without it, a room blocked on a new project's folder-trust dialog could not be answered without a terminal. The service takes the display from its own environment, or else from `systemctl --user show-environment`.
   - **Cross-site requests.** A POST authenticated by cookie or ticket must carry the lounge's own `Origin` and the header `x-maitre-request: 1`, or it gets 403 and does nothing. The CLI sends the token in the `x-maitre-token` header instead, which no other website can know. Request text travels only as a file and through the router, never in a shell string.
2. **Room chat in the panel (M5).**
   - The agent panel gets a "conversation" tab with the room's latest messages (read with `herdr agent read`) and a field to send (delivered with `herdr agent prompt`).
   - The "open tab" button focuses the room's herdr tab, for whoever wants the terminal. It shipped early, in M2b, as "Open in terminal" (item 1).
   - Text read from the room is always rendered as text.
3. **Icon and global shortcut (M2b, done).**
   - **The lounge as a service.** `maitre serve` is the live lounge with no window. `maitre setup` installs it as a `systemd --user` unit, `maitre`, that starts with the graphical session (`After=` and `WantedBy=graphical-session.target`, so the herdr server it may start inherits `DISPLAY`) and restarts on failure. The unit uses `KillMode=process`, so stopping or restarting it leaves the rooms and the herdr server running. Without the unit, `maitre open` and `maitre prompt` start `maitre serve` in the background.
   - **The lounge file.** The running lounge writes `$MAITRE_HOME/lounge.json` (`port`, `token`, `pid`; mode 0600). The token is made once and kept: on exit the pid becomes 0, so a restart keeps open windows' cookies valid. A lounge counts as live when its process exists and `GET /api/ping` answers with the same pid; only then is the token sent to that port. One lounge runs per `MAITRE_HOME`: a second `maitre serve` exits 0, so the unit does not loop while a terminal lounge runs, and `maitre` reuses a live lounge instead of creating its lounge tab.
   - **Tickets.** No window gets the token in its URL. Each window opens with a ticket in its command line, valid once and for 60 s, which the page trades for the token as the usual cookie, so whoever redeems a ticket first holds the token (see the threat model in §3). `maitre open`, `maitre prompt` and `maitre` get it from the lounge (`POST /api/ticket` with the token header); `maitre lounge` issues its own. A `?key=` URL is printed only by `maitre lounge`, for its own terminal, never by `maitre serve`, whose output lands in the journal.
   - **The icon.** A "maître" `.desktop` file opens the lounge as an app (`<wrapper> open`, `StartupWMClass=maitre`); its "Open in terminal" action runs `maitre`.
   - **The quick prompt.** A global shortcut (default Super+M, configurable) runs `<wrapper> prompt`, a small pixel prompt window (about 560×180) in the center of the screen. Enter sends the request as in item 1. The window closes itself 3 s after a dispatch and stays open on a question, an error or `needsYou`. Chrome ignores size and position flags when its profile is already running, so the page sizes and centers itself. For the same reason a lounge window opened while the prompt is up inherits the prompt's size; the lounge page grows itself to 1280×800 (clamped to the work area) and centers itself when it opened smaller than 640×400, and leaves a larger window alone.
   - **Super+M is freed from GNOME** (owner's decision, 26-11-2026). GNOME binds Super+M, with Super+V, to `toggle-message-tray`. Setup removes only Super+M from that list and records the old value; `--uninstall` restores it if Super+M is still missing there. Any other binding on the chosen key makes setup skip the shortcut and name the binding that holds it.
   - **The wrapper.** The unit, the icon and the shortcut run `$MAITRE_HOME/bin/maitre`, a small script with the absolute Node path, since none of them loads nvm. When that Node or the clone is gone, it says to re-run setup (stderr, plus `notify-send` except under the service, where `Restart=on-failure` would repeat it) and exits 1. `~/.local/bin/maitre` is only a copy for the terminal.
   - **Setup rules.** Every file setup writes carries the line `# Managed by maitre setup`, and a file without it is never overwritten. Each change is recorded in `$MAITRE_HOME/installed.json`, so `--uninstall` undoes exactly that and keeps maître's data. `--dry-run` prints every action and changes nothing.
   - On GNOME the shortcut is a `gsettings` custom keybinding; in other environments, setup prints the command and the README shows how to bind it by hand.
4. **Notification with buttons (M5).** When a room gets stuck, a desktop notification arrives with the options (A/B/C) as actions, via `notify-send --action` or D-Bus. The choice follows the same path as `POST /rooms/:id/answer`. The lounge bell keeps ringing.

## 7.1 Designer's decisions (open to review)

- **An inactive room gives up its seat.** When the room is on the couch or at the bar (PR open), the `claude` process is stopped after 30 min idle and the doorman's seat is freed.
  - The room keeps its session id, worktree and branch.
  - To wake it, maître runs `claude --resume <id>` in a new tab. This also covers a machine reboot.
  - A new request on the topic of a room on the couch wakes that room. For a closed room, the router creates a new room that is born with the old one's minutes.
- **After the PR is open: notify only.** The daemon polls CI and review through `gh`. When CI fails or a comment arrives, the room gets a notice in the lounge (orange balloon, no bell) and a line in the reception. maître does not prompt the room on its own. A `pr.autoWake` option (default `false`) exists for whoever wants it to wake the room by itself.
- **A PR closed without merge** counts as closed: the room closes with minutes and the branch stays.
- **Room without code:** on close, the files in its scratch folder move to `memory/rooms/<room>/`, never deleted.
- **Multi-repo room:** a room can have more than one worktree (1:N). It shows on the main project's floor, with a small sign for the others.
- **The user's global rules apply in rooms**, because they are the user's own Claude Code. `room-AGENTS.md` only pins what belongs to maître: use the worktree and branch maître created, do not create another, and declare waits and blocks with `maitre status`.
- **The 5k-token target** applies to the `route` call. The reception runs with setting sources off (spike 0), so personal settings, hooks and plugins stay out; Claude Code still loads the user's and organization's `CLAUDE.md`, and the guard hook keeps it to the `maitre` allowlist. The 1,500-word ceiling applies to its contract.
- **The building gets its own mockup before M4:** facade, elevator, lobby with sidewalk, and terrace. It is approved before code.

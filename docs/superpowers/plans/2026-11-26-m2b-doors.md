# maître M2b — The Doors Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Use maître without a terminal: after `./setup`, the lounge runs as a login service, a click on the maître in the lounge or a global Super+M prompt sends a request straight to the router and the room walks in, and an app icon opens the lounge.

**Architecture:** `maitre serve` is the live lounge without a window, owned through `$MAITRE_HOME/lounge.json` (stable port and token). The live routes gain `POST /api/reception` (store request → same router → same dispatch, serialized), `POST /api/rooms/:room/terminal` and `POST /api/ticket`; windows open with one-time tickets in a dedicated Chrome profile. `maitre setup` installs a Node-pinned wrapper, a `systemd --user` unit, a `.desktop` entry with icons and a GNOME custom keybinding, all recorded in a manifest that `--uninstall` reverses.

**Tech Stack:** Node ≥ 20, TypeScript strict, `node:test`, zero runtime deps; herdr 0.8.x, Claude Code 2.1.x, Chrome/Chromium, systemd user manager and GNOME `gsettings` as external programs.

**Spec:** `docs/superpowers/specs/2026-11-26-m2b-doors-design.md` (local, git-ignored by the repo; approved by the owner on 26-11-2026, including its "Decisions from the builder check") and `docs/design.md` §6.8.1 items 1 and 3. Approach picked by the owner: the lounge and the prompt talk **straight to the router**, never to the Claude reception.

**Out of M2b:** chatting with a room or answering a stuck room from the lounge (M5); doorman, queue, janitor (M3); shortcut registration outside GNOME; macOS/Windows.

## Global Constraints

- English everywhere; zero runtime deps; Node ≥ 20; TypeScript strict.
- **Never write Claude Code config** (`~/.claude/settings.json`, `~/.claude.json`, `~/.claude/*`). Setup touches only the files and settings listed in Task 7.
- **No user text in a shell string.** Request text travels only as a file under `$MAITRE_HOME/reception/requests/` and then through the existing router/dispatch code.
- **No token in argv.** Every window opens with `?ticket=<t>`; the token is only ever in `lounge.json` (0600), the HttpOnly cookie, or the `x-maitre-token` request header.
- **Server binds 127.0.0.1 only**; the existing Host check and `SameSite=Strict` cookie stay; GET without `Origin` stays allowed.
- **Every non-GET request authenticated by cookie or ticket** must carry `Origin` equal to `http://127.0.0.1:<port>` or `http://localhost:<port>` **and** `x-maitre-request: 1`; otherwise 403 and no side effect. A request authenticated by a valid `x-maitre-token` header (the CLI) needs neither, since no cross-site page can know the token.
- `lounge.json` = `{ "port": number, "token": string, "pid": number }`, mode 0600; token = 32 random bytes hex, generated once and reused; port starts at 8737 with the existing next-free fallback.
- **Liveness of a lounge:** the unauthenticated `GET /api/ping` (Host check still applies) answers 200 `{ "app": "maitre", "pid": <pid> }` within 2 s and the pid equals the one in `lounge.json`. The token is never sent to a port before that check passes. `maitre serve` never prints a `?key=` URL (it would land in journald); `maitre lounge` in a terminal still does.
- **Tickets:** 32 random bytes hex, valid 60 s, single use, created by `POST /api/ticket` with `x-maitre-token`.
- **Reception endpoint:** body JSON `{ "text": string, "answers"?: string }`, max 16 KiB, `text.trim()` non-empty; `answers` is a request id (`/^[0-9]{1,12}$/`). Responses: `{ "kind": "question", "id", "text" }` | `{ "kind": "dispatched", "id", "room", "lines": string[], "needsYou": boolean }` | `{ "kind": "error", "message" }`. `lines` are the dispatch result lines only (not the `route … →` summary); `needsYou` is true when the room waits on the folder-trust question or dispatch produced a warning. One request runs at a time; at most 3 wait (more → 429 "the maître is busy, try again"); the reply ceiling is 150 s (→ 504; above router 60 s + fetch 25 s + trust 30 s), and a timed-out job keeps its slot until it really ends, so jobs never overlap.
- **Windows:** Chrome/Chromium `--app=<url>` with `--user-data-dir=$MAITRE_HOME/chrome` and `--class=maitre`; the prompt window about 560×180, centered when the screen size is known; fallback `xdg-open <url>`.
- **Terminal:** `x-terminal-emulator -e <herdr> --session <session>`, fallback `gnome-terminal -- <herdr> --session <session>`; display vars from the process env, else from `systemctl --user show-environment`, else 503.
- **Setup marker:** every file setup writes contains the line `# Managed by maitre setup` (`.desktop`, unit, wrappers); a target that exists without it is never overwritten.
- **Wrapper:** the unit, the `.desktop` file and the shortcut always run `$MAITRE_HOME/bin/maitre` (maître's own, always writable). `~/.local/bin/maitre` is only a convenience copy for the terminal, skipped with a note when a foreign file is there.
- **Shortcut:** default `<Super>m`; GNOME custom keybinding path `/org/gnome/settings-daemon/plugins/media-keys/custom-keybindings/maitre/`; when the accelerator is `<Super>m` and `org.gnome.shell.keybindings toggle-message-tray` holds it, remove only `<Super>m` from that list and record the old value (owner decision).
- Everything spawned by the service gets `cleanEnv` (src/env.ts).
- **The service must not own the rooms.** Rooms and the herdr server it may start live on after `systemctl --user restart|stop maitre`: the unit uses `KillMode=process`.
- **Never touch the real desktop before Task 8 step 3.** No task or test runs the real `gsettings`, `systemctl --user` (except the read-only `show-environment`), `xdg-desktop-menu` or writes under the real `~/.config`, `~/.local` or `~/.maitre`. Tests put their fakes first on PATH and assert the fake was the one called; temp `HOME`/`XDG_*` do not isolate dconf or the user manager.
- Commits: repo-local identity; messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; branch `feat/m2b-doors` in worktree `~/maitre--worktrees/m2b`; PR to `main` (assignee `danielrdg`), merged with `--rebase` on the owner's word. No work email or employer name in tracked files; scan with `MAITRE_FORBIDDEN_WORDS` (runtime env only) before every push.

## Review Focus

1. **Cross-site POST** (no `Origin`, foreign `Origin`, missing `x-maitre-request`, `text/plain` form body, valid cookie) → 403, no request file, no route. → tests in Task 2 and Task 4.
2. **Stale or foreign `lounge.json`** (dead pid, a different program on the port, a wrong token) → not live: `serve` takes ownership, `open`/`prompt` never send a ticket request to a lounge that failed the probe. → tests in Task 2 and Task 5.
3. **Hostile or odd request text** (`$(rm -rf ~)`, backticks, newlines, 16 KiB + 1, whitespace only, non-JSON, `text` a number, `answers` not an id or unknown) → stored verbatim or rejected with 400 before anything is stored. → tests in Task 4.
4. **Setup on a lived-in desktop** (run twice; foreign `~/.local/bin/maitre`; another custom keybinding on `<Super>m`; `toggle-message-tray` already changed by the user) → no duplicates in `custom-keybindings`, foreign files untouched, uninstall restores exactly what it recorded and nothing else. → tests in Task 7.
5. **Service without the login shell** (no nvm on PATH, no `DISPLAY` in the unit env) → the unit runs an absolute Node through the wrapper with the PATH captured at setup; the terminal endpoint falls back to `show-environment` or answers 503 with the hint. → tests in Task 4 and Task 7.

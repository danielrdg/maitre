# Spike M2b: app windows and the service display

Date: 26-11-2026. Ubuntu, GNOME Shell 46 on X11 (1920x1080), Google Chrome 158.0.8127.36, snap Chromium 157.0.8103.38.

This is the public summary of the spike behind [M2b](../design.md) (desktop "doors": the lounge as an app window, a small centered prompt window, a `systemd --user` service). Everything ran against a throwaway page on `127.0.0.1` with a temporary `--user-data-dir`. Paths below are neutralized (`~` for the home directory). Sample sizes are small: every row is one to three runs.

## TL;DR

1. **`--app --class=maitre --window-size --window-position` works, but only when the profile is not running yet.** On a cold start the window opens at the exact size and position asked, and `WM_CLASS` is `"<host>", "maitre"`. Saved window placement in the profile did not override the flags.
2. **A second `--app` launch into a profile that is already running ignores `--window-size` and `--window-position`.** The new window opens with the first window's geometry. The launcher returns in about 0.13 s with exit code 0. It makes no difference whether the URL has another host.
3. **The page can fix its own geometry.** `window.resizeTo(w, h)` and `window.moveTo(x, y)` from page JS, with no user gesture, worked in an `--app` window of a running profile (400x300 at 100,100, then 560x180 at the computed center). This is the way to place the prompt window while the lounge window keeps the profile busy, and the way out of the reverse case: a lounge window opened while the prompt keeps the profile busy inherits 560x180, so the lounge page grows itself to 1280x800 (clamped to the work area) and centers itself when it opens smaller than 640x400.
4. **`window.close()` closes an `--app` window** opened from the command line (4 windows to 3, 3 s after load, no gesture).
5. **The browser process exits right after the last window closes.** The cold-start launcher stays in the foreground until then. A relaunch a moment after the close is a clean cold start, honouring the flags (no race observed).
6. **Snap Chromium cannot use a profile in a hidden directory of the home directory.** `--user-data-dir=~/.maitre-spike-tmp/chrome` fails with `Failed to create .../SingletonLock: Permission denied`, exit code 21. A visible directory (`~/maitre-spike-tmp-vis`) works. So `$MAITRE_HOME/chrome` (default `~/.maitre/chrome`) requires Google Chrome (Chromium is never used for it: the apt stubs exec the snap).
7. **The user manager environment has what Task 4 needs:** `systemctl --user show-environment` lists `DISPLAY`, `XAUTHORITY` and `PATH`. `WAYLAND_DISPLAY` is absent (X11 session).

## Recipe (what Task 5 uses)

```
google-chrome \
  --user-data-dir=$MAITRE_HOME/chrome \
  --class=maitre \
  --no-first-run --no-default-browser-check \
  --app=<url>?ticket=<t> \
  --window-size=560,180 --window-position=<x>,<y>
```

- Spawn detached with `stdio: 'ignore'` and `unref()`: a cold launcher lives as long as the browser, a warm one exits at once.
- Keep `--window-size` and `--window-position` for the cold case (they are exact). Do not rely on them for the warm case.
- **The prompt page positions itself.** On load it calls `resizeTo(560, 180)` and `moveTo(...)` with the screen work area. Measured here: `screen.availLeft=66`, `availTop=32`, `availWidth=1854`, `availHeight=1048`. `moveTo` takes absolute screen coordinates, so center with `availLeft + (availWidth - w) / 2` and `availTop + (availHeight - h) / 2`. A first try that forgot the offsets landed 66 px left of the true center of the work area. No `xdpyinfo` or `xrandr` is needed on the Node side.
- Both windows can share one profile directory. The cost is the warm-launch rule above, which self-placing pages cover: the prompt always sizes and centers itself, and the lounge does so only when it opened smaller than 640x400, so a lounge window the user sized is left alone.
- **Fallback if self-positioning is refused:** an unpositioned window, with the prompt staying open in a "done" state (the spec's fallback). `xdg-open <url>` remains the last resort when Google Chrome is not found.
- **Binary choice:** use `google-chrome` or `google-chrome-stable` only. Treat every `chromium` / `chromium-browser` as snap-suspect and never launch it with the maître profile: on Ubuntu the apt packages are stubs that exec the snap, so a path check cannot tell them apart, and the snap exits with code 21 on a hidden profile directory. Without Google Chrome, fall back to `xdg-open <url>` (a plain browser tab, no size control). The current `src/open-app.ts` tries bare `chromium` with no profile; that attempt must go once the profile is added.

## What was checked

### (a) Size, position and `WM_CLASS`

Window geometry was read with `xwininfo -id` after finding the window through `xprop -root _NET_CLIENT_LIST` plus `xprop -id <id> WM_CLASS` (`xdotool` and `wmctrl` are not installed).

| Case | Flags | Result |
| --- | --- | --- |
| Cold start | `--window-size=560,180 --window-position=680,450` | 560x180 at 680,450. `WM_CLASS = "127.0.0.1", "maitre"` |
| Cold start, profile had saved placement | `--window-size=480,220 --window-position=200,300` | 480x220 at 200,300 |
| Warm, same URL host | `--window-size=400,300 --window-position=100,100` | 560x180 at 680,450 (the first window's geometry) |
| Warm, other host (`localhost`) | same | same as the first window |
| Warm, page calls `resizeTo(400,300); moveTo(100,100)` | | 400x300 at 100,100 |
| Warm, page centers itself | `resizeTo(560,180)` + `moveTo` | 560x180, `outerWidth`/`outerHeight` 560x180 |
| Cold start right after the last window closed | | flags honoured, new window `WM_CLASS` still `"127.0.0.1", "maitre"` |

- `WM_CLASS` keeps `maitre` as the class in every window, warm ones included. The instance name is the page host. A `.desktop` file for the lounge should use `StartupWMClass=maitre` (matching in the GNOME dock was not tested).
- `_NET_WM_WINDOW_TYPE` is `NORMAL`. `_NET_FRAME_EXTENTS` reports 37 px on top (the title bar); `xwininfo` and `outerHeight` still report the 180 px of the content.
- A `window.open(..., 'popup,width=..')` from a timer with no user gesture opened nothing (blocked). It was not tried with a gesture and is not needed.

### (b) `window.close()`

A page with a 3 s timer calling `window.close()` closed its `--app` window: the window count went 4 to 3. Not tested: a page that navigated first (a window with more than one history entry may refuse). Task 5's prompt page should close itself from its own first page and not after a navigation.

### (c) Isolation from the normal Chrome profile

Each launch used a fresh temporary `--user-data-dir`, so Chrome started its own browser process and never forwarded to a running normal Chrome. With `--no-first-run --no-default-browser-check`, no welcome or default-browser page opened: the only new window per launch was the app window. Only processes whose command line carried the temporary profile were started or stopped.

### (c2) Snap Chromium and a profile under the home directory

- Hidden directory (`~/.maitre-spike-tmp/chrome`): exit code 21, `Failed to create ... SingletonLock: Permission denied`, plus `update.go` mount-namespace warnings from snapd. No window.
- Visible directory (`~/maitre-spike-tmp-vis`): started, opened an app window with `WM_CLASS = "127.0.0.1", "Chromium"` (that run had no `--class`; `--class` and the size flags were not retried with snap in the visible directory).
- Conclusion: `~/.maitre/chrome` needs Google Chrome. Chromium is not used for it, since the apt stubs exec the snap. Moving the profile to a visible directory only to suit snap is not worth it.

### (d) Service display

`systemctl --user show-environment` (read-only, names only checked):

| Variable | In the user manager environment |
| --- | --- |
| `DISPLAY` | present (`:`-style X11 display) |
| `XAUTHORITY` | present (an absolute path) |
| `PATH` | present |
| `WAYLAND_DISPLAY` | absent |

So a service that has no `DISPLAY` of its own can read it from `systemctl --user show-environment`, as Task 4 plans. On a Wayland session `WAYLAND_DISPLAY` would be expected there instead; not tested.

## Not verified

- Wayland sessions (this machine is X11): whether `moveTo` is honoured there is unknown.
- The `.desktop` match against `StartupWMClass` in the dock, and the shortcut, belong to Task 8.
- Chrome versions other than 158.
- `window.close()` after in-page navigation.

## Cleanup

All windows and every browser process that used a temporary profile were closed, the throwaway server was stopped, and the temporary profile directories (including the two under the home directory) were removed. `~/.maitre` was never created or touched. No unit was installed and no `gsettings` or `systemctl --user` command other than `show-environment` ran.
